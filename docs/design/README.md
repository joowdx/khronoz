# khronoz — design (draft, 2026-09-08)

Single-word models, plural tables, ULID keys, Postgres. Every table carries `agency_id`; the agency is the tenant. Global defaults belong to the platform agency row, never to null. Integrity is enforced in Postgres, see 07-constraints.md.

Read 00-principles.md first, then one file per concern. Each concern file has a mermaid ERD.

6. Decided 2026-09-08: `Exemption`.
7. Slots as fixed-shape json on the shift, copied into the workday snapshot. Shape settled in 04-scheduling.md: per pair `in, out, grace, window`; times past 24:00 (`"30:00"` is 06:00 the next day) replace the `overnight` flag and cover 24- and 48-hour duties; `flex` minutes on the shift replaces the wide-window flexi idea. Examples there for standard, flexitime, CWW, hospital rotation, 12-hour, 24/48 duty, Ramadan. Confirmed 2026-09-08.
8. Decided 2026-09-08: `Unit`.
9. Decided 2026-09-08: `Ledger` is a table, one row per employee-month created by the first workday; `workdays.ledger_id` is a required FK.
10. Decided 2026-09-08: all deltas D1–D13 accepted and folded into the concern files. D5 stores raw `excess` on the workday, compensable overtime is the ledger view against `Overtime`. The table below is kept as the audit trail.
11. Decided 2026-09-08 under "if it is a real improvement then we do it": global rows are owned by the platform agency row instead of `agency_id` null; every table carries `agency_id` with paired foreign keys; timelog resolution is done by database trigger, not by the app. Confirmed 2026-09-08.

12. Decided 2026-09-08: D8 is an `attestations` table, one row per role per ledger, roles listed per agency in settings, signers resolved from `Unit.head_id`. Attestations require a locked ledger; unlocking requires removing them first.
13. Decided 2026-09-08: cross-midnight punches belong to the workday the shift started on, in that month; a timelog at T can only serve dates T − 3 to T; a ledger cannot lock while an out is still pending. CS Form 48 prints later-day punches with a day marker.
14. Decided 2026-09-08: the shared-row owner is the **platform** agency, found by a `platform` boolean with a partial unique index, not by a magic code. Its rough edges are handled: an Eloquent global scope hides it from every agency list; superusers act inside a chosen agency so scoping has one code path; defaults are copied into each new agency at onboarding and copies carry `origin_id`, so drift is visible and refreshable; employees, units, terminals and groups refuse the platform row by trigger. Say if not.

15. Decided 2026-09-08: tier 3 agency settings are one `settings` jsonb column on `agencies`, shape checked by a Postgres function, read through one typed PHP class; an `audits` table filled by a generic row-level trigger on rosters, exemptions, overtimes, enrollments, timelog voids, ledger locks, attestations, shifts and schedules is in v1, with `user_id` from a session variable the app sets per request; employee logins are created by HR invite only, and an agency whose staff never log in drops `employee` from its attestation chain.

16. Decided 2026-09-09: the biometric device model is `Terminal` (`terminals`, `terminal_id`). Passport's device-authorization model keeps `Device`/`devices`, installed in 4d067d4. Decision 3 is superseded.
17. Decided 2026-09-09: permissions instead of a role enum. `users.permissions` is a jsonb array of strings from one PHP enum with a Postgres shape check; presets are code, not rows. Decision in 02-access.md rule 4 supersedes "roles are a single enum".
18. Decided 2026-09-09: auth is hand-rolled on framework primitives (Fortify's stable line stops at Laravel 12); invite-only logins; Google and Apple sign-in through Socialite only for already-invited emails.
19. Decided 2026-09-09: exemption type `personal`. Personal pass slips, also called locator or OB slips, are recorded and printed but never excuse minutes: undertime still counts and is charged to leave (Omnibus Rules on Leave §34). The official-business type stays `pass`. `Exemption::excused()` is false only for `personal`, and the attendance deriver consults it before excusing tardiness, undertime or absence. On CS Form 48 an exempt whole day prints the exemption type or its order reference across the time columns; a partial day keeps its punches and marks the excused side.
20. Decided 2026-09-09: `Order` is phase 2. Office, memorandum, special and travel orders are covered in v1 by `Exemption` (`travel`, `business`, `pass`, with `reference` holding the order number) and by `Overtime.reference`. An issuance parent (`agency_id, kind, number, title, issued_at, starts, ends, revoked_at`, a nullable `order_id` on both children, fan-out per employee per day, prospective revocation) is deferred to phase 2 together with scanned attachments.
21. Decided 2026-09-09: `shifts.color`. The roster grid colours each shift from a fixed eight-slot ramp, stored as `shifts.color smallint` 1 to 8 on the shift row, not derived. It defaults to the lowest index the agency is not already using and wraps at 8; HR may change it; copies from the platform agency carry the origin row's index; `Off` and `Remote` never take an index because they are drawn from empty `slots` and the `remote` flag. Hashing an identifier was rejected: it looks stable but collides inside one agency and cannot be corrected.
22. Decided 2026-09-09: the interface design. The product's visual language is specified in 08-interface.md and shown in `mockups/`: white canvas, hierarchy from type and rules rather than boxes, pure achromatic neutrals, one violet accent, colour reserved for data, Plus Jakarta Sans throughout, a sticky title bar carrying the page title (the month stepper is the title on month-scoped pages), validation errors right-aligned on the label row, dark mode as `data-mode` on the root element, and the roster grid as the one memorable element. Earlier directions (the framework's default look, a navy or dark shell, neumorphism, a plum and gold duotone) were rejected by the owner.
23. Decided 2026-09-09: CS Form 48 places each punch by its clock time. A punch prints in the column its own clock time falls in, AM before 12:00 and PM from 12:00, with the next-day marker where the punch belongs to a later date, so a single-pair night shift of 22:00 to 06:00 prints as a PM arrival and an AM departure marked `⁺¹`. This supersedes the wording in 06-attendance.md that a one-pair shift prints its arrival in the first column and its departure in the last, which put a 22:00 arrival in the AM column. Refined the same day, when the marketing page's own sample proved the rule incomplete: the form carries four time columns, so two pairs sitting inside one half of the day (14:00 to 18:00 with 19:02 to 22:00, or a night shift broken at 02:00) cannot be split across headings the paper does not have, and those print positionally, slot 1 in the first pair of columns and slot 2 in the second. Three or more pairs print the first in and the last out only. Day markers carry the dates in every case. Say if not.
24. Decided 2026-09-09: the function this product serves is the **timekeeper**, not "HR". `Preset::Hr` becomes `Preset::Timekeeper` (value `timekeeper`, label `Timekeeper`), the attestation role `hr` becomes `timekeeper`, and every label naming the function follows: the `ledgers.attest` permission label, the invite matrix's attest checkbox, the preset segmented control in 08-interface.md, and the artboards that draw them. Two other uses of "HR" were separated out rather than renamed with it. The office that sent your invitation is now **the administrator** — sign-in, forgot-password, the users empty state and `auth.invited` say so — and prose describing the customer says what the office does: an office's *timekeeping staff*, a Philippine *government office*, a government *personnel system*. Presets are never persisted, so the enum's string value changed freely. The wording inside decisions 15 ("created by HR invite only") and 21 ("HR may change it") is superseded by this one; the log is a dated record of what was decided then and is never rewritten, so read the concern files for the live spec. `HR` in `../reference/csc-rules.md` is the hourly rate of JC 2 s. 2015 §9.3 and is untouched.
25. Decided 2026-09-09: `Group` and `Member` are dropped, and `employees.status` is replaced by `employees.tags`, a json array of free-form agency labels that no rule reads. Groups and tags were the same idea twice — both were "how you pick many employees at once" — and a group additionally carried effective dates it never needed. What is left has three non-overlapping jobs, written out as rule 5 of 01-organization.md: units are the formal structure, one placement at a time through `Deployment`; tags are labels on the employee and the way you select many for an ad-hoc bulk action; a `Team` (decision 26) is the only one of the three that decides what a person is expected to work. A fact you filter by is a tag; a rotation you belong to is a team; `meta` is inert payload nothing filters on. `enum status` went the same way: appointment nature varies by agency and by issuance, no rule in the system reads it, and a fixed set khronoz has to keep current is worse than a label the agency owns. `tags` ships with no shape check yet, recorded as an open item under `employees` in 07-constraints.md.
26. Decided 2026-09-09: `Team` is a named `(schedule, anchor)` cohort — `id`, `agency_id`, `name`, `schedule_id`, `anchor` — specified in 04-scheduling.md and 07-constraints.md and implemented in Milestone 3. Three hospital teams are one schedule and three anchors. A team has no membership table: the rosters carrying its `team_id` *are* its membership, so who was on it in March is answerable from their date ranges, and one employee on two teams at once is already impossible under the roster exclusion constraint. Assigning a team writes one roster per employee, each copying the team's schedule and anchor and pointing back with `team_id`; an ad-hoc set is a tag filter plus select-all, writing rosters with `team_id` null. Either way resolution reads one roster row. A roster's `schedule_id` and `anchor` may differ from its team's, deliberately: `team_id` records where the assignment came from, not a rule about what it produced. The `agency_not_platform` trigger list becomes `employees, units, terminals, teams`; Milestone 2 still applies it to `employees` and `units` only, `terminals` is Milestone 5 and `teams` is Milestone 3.
27. Decided 2026-09-10: `employees.tags` ships **with** a shape check. The column is a jsonb array of distinct, non-empty strings, bounded at 20 elements, enforced in the DDL by `employees_tags_valid` (`CHECK (string_set_valid(tags))`) and `employees_tags_bounded` (`CHECK (jsonb_typeof(tags) <> 'array' OR jsonb_array_length(tags) <= 20)`, written that way because Postgres does not order CHECK evaluation), plus `CREATE INDEX employees_tags ... USING gin (tags)` for `tags ? 'x'`. `string_set_valid(jsonb)` is the shared function `users.permissions`' own check already proved out — array, every element a string, no duplicates, and non-empty elements — so the next jsonb label set reuses it and brings its own bound; the empty array stays legal, being the column default. A per-tag character bound (40) is deliberately the Form Request's, not the database's: the length an agency may type is a UI decision that will change, and a CHECK is the wrong place to keep a changing number. This supersedes the closing sentence of decision 25, "`tags` ships with no shape check yet, recorded as an open item under `employees` in 07-constraints.md" — true when it was written, and closed by the next task of the same milestone; 07-constraints.md's `employees` section carries the live spec and the constraint suite tests both checks. Decision 25 itself stands as written: the log is a dated record of what was decided then and is never rewritten (decision 24).

28. Decided 2026-09-10: `employees.hired_at` and `employees.separated_at` are removed. Deployment ranges are the employment history: an open range is current employment, closed ranges preserve prior service, and a new range after a gap records rehire under the same employee number and DTR trail. A person without a placement is not yet started for timekeeping; tags can distinguish departure from a gap without adding a computation rule. This eliminates the former deployment-containment gap rather than adding a cross-table trigger. Unit-head eligibility requires a non-deleted employee with an open deployment, in both the picker and the two Form Requests. Ending a placement is PATCH `employees/{employee}/deployments` with an inclusive `ends`, implemented by one conditional UPDATE of rows whose `ends IS NULL`; zero affected rows redirects to the employee profile with the error “No open placement to end.” A stale submission must never re-date closed history, and no database constraint would stop that rewrite, so the predicate is essential. The former `SeparateEmployee` action is folded into that controller operation. Removal remains distinct: `RemoveEmployee` closes a started open deployment on bare `today()`, deletes a future open deployment that would otherwise become an empty range, then soft-deletes the employee, all in one transaction. Closed history is retained and continues to restrict removal of its unit. This supersedes the employment-date fields and containment gap in 01/07, and the handoff's instruction to call `SeparateEmployee` from destroy. M2 is unreleased and unpushed, so the original employees migration is edited in place; no upgrade migration is needed.
